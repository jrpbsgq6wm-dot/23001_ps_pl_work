# ChatGPT：Linux 端 DSP 回读与 600 m 大数据上传边界说明

> **版本日期：** 2026-09-21  
> **适用工程：** `D:\Prj_2026\23001\linux\20260916`  
> **本文目的：** 明确 600 m 大帧、DSP NREAD 回读数据和 Linux 上传数据的边界，避免把“PL 生成的整帧长度”和“DSP 实际返回的数据长度”混为一谈。

---

## 1. 当前裁定

本文件先把实际数据流分清，再讨论 Linux 的回读和上传边界。

PL 产生每条波束记录后，数据有两条并行/流水化去向：

```text
                         ┌─→ Frame DDR：完整波束 Frame 留存（调试查看）
IQ → PL 波束形成 → 波束数据 ┤
                         └─→ SRIO/SWRITE → DSP
                                           ↓
                                    DSP 处理结果
                                           ↓
                                  DSP/NREAD → NREAD DDR
                                           ↓
                              Linux 分块读取 → 上位机
```

这里的“边向 DSP 发边写 DDR”是 PL 内部流水路径：PL 不必等待整帧写完 Frame DDR 后再发 DSP，也不应让 Linux 去读取 Frame DDR 代替 DSP 处理链路。

当前正式工程采用以下边界：

```text
1. Frame DDR 中的完整波束 Frame：只作为调试留存和问题定位数据；正式业务不由 Linux 读出并上传上位机。
2. PL → DSP 的 SWRITE：发送完整波束 Frame，600 m 长帧也按 PL/DSP 协议正常流转。
3. DSP → PL 的 NREAD：返回 DSP 实际结果，当前按最大约 4 MiB 设计。
4. Linux → 上位机：只读取 NREAD DDR 中的 DSP 返回结果，不上传 Frame DDR 中的完整波束 Frame。
```

因此，“600 m 暂不上传”不是说 PL 不生成、也不是说 PL 不把长帧发给 DSP；准确含义是：正式 Linux 上传链路的输入只有 DSP NREAD 返回区，Frame DDR 只留给调试阶段查看。

A、B 两条软件/硬件职责应明确分开：

```text
A. PL/DSP 工作链路
   IQ → CBF →（Frame DDR 调试留存 + SRIO/SWRITE 发 DSP）→ DSP → NREAD 回写 DDR

B. Linux 正式上送链路
   NREAD DDR 中的 DSP 返回数据 → 分块读取 → 上传上位机

C. 调试查看链路（非正式上传链路）
   Frame DDR 中的 PL 波束 Frame → 按需读取/导出/分析；不进入正常上位机上传流程
```

## 2. 长度和存储区必须分开

Linux 端不能用一个“帧长度”变量覆盖所有路径。至少应区分下面四个量：

| 名称 | 含义 | 所属路径 | 当前口径 |
|---|---|---|---:|
| `frame_bytes` | PL 生成的完整波束 Frame 长度，也是通过 SWRITE 送 DSP 的逻辑长度 | PL → Frame DDR / SWRITE → DSP | 可很大；2666 点约 16.3 MB，600 m 约 196.5 MB |
| `frame_ddr_bytes` | Frame DDR 中为调试留存的完整波束 Frame 长度 | PL → Frame DDR | 通常等于 `frame_bytes`；只用于调试查看 |
| `nread_bytes` | DSP 通过 NREAD 返回并写入 NREAD DDR 的实际结果长度 | DSP → NREAD DDR | 最大约 4 MiB |
| `upload_bytes` | Linux 从 NREAD DDR 读取并上传上位机的长度 | NREAD DDR → Linux → 上位机 | `≤ nread_bytes`，当前最大约 4 MiB |

逻辑关系为：

```text
frame_ddr_bytes ≈ frame_bytes       （PL 调试留存副本）
frame_bytes     → SWRITE → DSP     （DSP 输入）
nread_bytes     ≤ 4 MiB             （DSP 返回结果）
upload_bytes    ≤ nread_bytes       （Linux 正式上传）
```

这里的 `≈` 只表示两条 PL 输出路径在逻辑内容和长度上对应；由于它们经过不同的 FIFO/发送流水线，不能把“Frame DDR 写入完成”误认为“SWRITE 发送完成”，也不能把某一条路径的完成信号直接替代另一条路径的完成信号。

正式工程中，以下关系不成立，必须禁止：

```text
nread_bytes  = frame_bytes
upload_bytes = frame_bytes
Frame DDR    = Linux 正式上传源
```

尤其不能因为 600 m 的 `frame_bytes` 约为 196 MB，就让 Linux 按 196 MB 读取 NREAD 区或把 Frame DDR 整帧上传上位机。

## 3. 各量程长度示例

当前工程的 PL Frame 长度口径：

```text
frame_bytes = 3730 + (IQ_POINTS - 10) × 256 × 24
```

典型值如下：

| 场景 | PL/SWRITE 完整 Frame `frame_bytes` | Frame DDR 调试留存 | DSP NREAD 返回上限 | Linux 正式上传范围 |
|---|---:|---:|---:|---:|
| 21 点 | 71,314 B | 71,314 B 左右 | ≤ 4 MiB | ≤ 4 MiB |
| 2666 点 | 16,322,194 B | 16,322,194 B 左右 | ≤ 4 MiB | ≤ 4 MiB |
| 600 m | 约 196,501,138 B | 约 196.5 MB（仅调试） | ≤ 4 MiB | 只上传 NREAD 返回，不上传 196.5 MB Frame |

注意：

- “Frame DDR 调试留存”表示 PL 在波束数据流水过程中保存的一份副本，不代表 Linux 正式业务必须把它搬到上位机。
- 600 m 的完整 Frame 仍可能由 PL 生成、写入 Frame DDR，并通过 SWRITE 分段发送给 DSP；“不上传”只约束 Linux → 上位机这条链路。
- 4 MiB 是当前 DSP 返回结果的工程上限，最终仍应以 `NREAD_LAST_BYTES` 和硬件协议约束为准。

## 4. 600 m 当前允许和禁止的操作

### 4.1 PL/DSP 正式工作链路允许

```text
1. PS 准备 IQ 输入区。
2. PL 读取 IQ 并执行波束形成。
3. PL 产生波束记录后，沿两条流水路径同时推进：
   a) 写入 Frame DDR，作为调试留存；
   b) 通过 SWRITE 分段发送给 DSP。
4. DSP 按协议接收并处理完整 Frame。
5. DSP 通过 NREAD 返回不超过 4 MiB 的结果。
6. PL 将 DSP 返回结果写入 NREAD DDR。
7. Linux 只读取 NREAD DDR 中的 DSP 返回结果，并按实际长度处理。
8. Linux 将 NREAD 返回结果分块上传上位机。
```

### 4.2 调试阶段允许

```text
1. 在确认不会破坏正式帧缓冲所有权的前提下，按需读取 Frame DDR。
2. 对 Frame DDR 留存数据做帧头、长度、记录内容、MD5/CRC 或算法对比。
3. 将 Frame DDR 数据导出到本地调试文件，供开发人员离线分析。
```

Frame DDR 的调试读取是旁路操作，不应接入正常 IRQ/NREAD 上传服务，也不能因为调试读取而清除或覆盖当前业务帧状态。

### 4.3 当前禁止

```text
1. Linux 按 frame_bytes 读取 600 m Frame 作为正式上传数据。
2. Linux 把 Frame DDR 的 196 MB 全帧复制到固定 30 MB 的 Image_Data。
3. Linux 把 Frame DDR 全帧一次性发送到上位机。
4. 用 frame_bytes 直接作为 DSP NREAD 返回长度。
5. 把 Frame DDR 的写入完成当成 DSP NREAD 完成。
6. 用旧的 5 MB 判断代替明确的 DSP 返回上限和 NREAD_LAST_BYTES。
7. 调试查看线程直接改写 Frame DDR 或 NREAD DDR 的原始内容。
```

## 5. Linux 端必须采用流式读取

正式上传源是 **NREAD DDR 中的 DSP 返回结果**，不是 Frame DDR。即使当前最大回读只有 4 MiB，也建议使用分块方式，不依赖整帧大数组。

推荐流程：

```text
等待有效 NREAD 完成事件
        ↓
读取 NREAD_EVENT_COUNT / NREAD_LAST_INFO / NREAD_LAST_BYTES
        ↓
确认本次事件对应的 NREAD DDR 数据
        ↓
得到实际 nread_bytes
        ↓
检查 0 < nread_bytes ≤ 4 MiB
        ↓
按 1 MiB～4 MiB 分块读取 NREAD DDR（当前基址 0x30000000）
        ↓
逐块校验/上传上位机
        ↓
不修改 NREAD 原始数据
```

PL 的 Frame DDR 只在调试工具或专项诊断命令中读取：

```text
正常业务：NREAD DDR → Linux → 上位机
调试查看：Frame DDR → 调试脚本/分析工具（不进入正常上传服务）
```

伪代码：

```c
#define DSP_RETURN_MAX_BYTES (4U * 1024U * 1024U)
#define UPLOAD_CHUNK_BYTES   (1U * 1024U * 1024U)

if (nread_bytes == 0 || nread_bytes > DSP_RETURN_MAX_BYTES) {
    reject_current_result();
}

for (offset = 0; offset < nread_bytes; offset += UPLOAD_CHUNK_BYTES) {
    chunk = min(UPLOAD_CHUNK_BYTES, nread_bytes - offset);
    send_all(upper_fd, nread_ddr + offset, chunk);
}
```

当前 `dry_to_upper()` 中的固定整帧缓存和旧协议解析必须与这个边界重新对齐。不要把“为了调试读取 Frame DDR”实现成“正式上传服务默认上传 Frame DDR”。

## 6. 当前代码需要重点修改的地方

### 6.1 不要用旧的 5 MB 限制作为协议定义

当前代码存在类似逻辑：

```c
if (All_lenth > 5000000) {
    continue;
}
```

新的约束应明确为：

```c
DSP_RETURN_MAX_BYTES = 4 * 1024 * 1024
```

并说明这是 **DSP 返回数据上限**，不是 PL Frame 上限。

### 6.2 不要用 `Image_Data[30000000]` 保存长帧

600 m 完整 Frame 约 196 MB，固定 30 MB 缓冲区不足；但正式 Linux 上传又不需要保存这份 Frame。

正式路径应为：

```text
NREAD DDR（DSP返回，≤4 MiB） → 分块缓冲 → 上位机
```

Frame DDR 的约 196 MB 数据只在调试查看时按需分块读取，不能复用正式上传缓冲区，也不能默认进入 `Image_Data`。

### 6.3 不要修改 NREAD 或 Frame DDR 原始数据

正式上传时，Linux 应把 NREAD DDR 中的 DSP 返回结果当作原始数据处理，不能在原缓冲区中修改温度、头字段或长度字段。调试查看 Frame DDR 时也遵循同一原则，解析或修补必须使用独立副本。

正确做法：

```text
原始 DDR 数据保留不动
解析副本单独转换
或直接分块原样上传/导出
```

当前正式业务不上传 Frame DDR 全帧；若需要导出调试数据，应使用独立调试工具和明确的长度，不得让调试路径改变正常 NREAD 上传状态。

### 6.4 帧格式必须按 BUILD_ID 分流

当前工程至少存在旧协议和新 24B 协议两种口径：

```text
旧版本：旧的@@ST/旧记录格式
0x124：@@@@整帧 + full_abs/corr_i/corr_q/angle 新24B记录
```

Linux 端不应只检查固定的 `@@ST`，也不能在不知道 BUILD_ID 的情况下直接按旧结构解析。

推荐：

```text
读取 CBF BUILD_ID
        ↓
0x124 → 新24B原始帧/新解析器
≤0x123 → 旧协议解析器
```

## 7. 中断和 NREAD 完成判据

NREAD 完成不能只看 UIO `read()` 返回，也不能只看 `nread_done` 单拍信号。

Linux 处理一次中断时应至少检查：

```text
1. IRQ_STATUS
2. EVENT_COUNT 是否增长
3. NREAD_LAST_INFO
4. NREAD_LAST_BYTES
5. SRIO/NREAD error count
6. 0x7C 的 read_busy/read_error/stuck
```

推荐判据：

```text
EVENT_COUNT 增长
&& NREAD_LAST_BYTES > 0
&& nread_bytes <= 4 MiB
&& read_error == 0
&& stuck == 0
```

处理顺序：

```text
read(/dev/uio)
  → 读取状态
  → 确认EVENT_COUNT增长
  → 读取NREAD数据
  → W1C清IRQ_STATUS
  → write(/dev/uio, 1)重新使能
```

不能只执行：

```c
read(uio_fd, ...);
write(uio_fd, &one, sizeof(one));
```

否则可能把旧中断或旧 NREAD 数据当成新结果。

## 8. 当前阶段的验收边界

### 8.1 2666 点

正式业务链路可以验收：

```text
PL 生成约 16.3 MB Frame
→ 一边写 Frame DDR 调试副本，一边通过 SWRITE 发送 DSP
→ DSP 处理
→ DSP 返回 ≤4 MiB 结果
→ PL 写 NREAD DDR
→ Linux 读取并校验/上传 ≤4 MiB 结果
```

调试时可以另外检查 Frame DDR 中的约 16.3 MB 数据是否正确，但这不是 Linux 正式上传验收项。

不能把“Linux 只收到 ≤4 MiB DSP 返回数据”误判为“2666 点完整 Frame 只有 ≤4 MiB”。

### 8.2 600 m

当前正式业务只验收：

```text
PL 是否能生成并流水化写入 Frame DDR，同时完成 SWRITE 发送
DSP 是否能处理长 Frame
DSP 返回结果是否不超过 4 MiB
NREAD DDR 写入是否正确
IRQ/EVENT_COUNT/NREAD_LAST_BYTES 是否正确
Linux 是否只上传 NREAD 返回结果
```

Frame DDR 的约 196.5 MB 完整数据可作为调试证据查看，但当前不作为 Linux 正式上传验收项。

当前不验收：

```text
Linux 上传 196 MB 完整 Frame
上位机保存完整 600 m Frame 作为正式业务数据
```

如果未来要开放 Frame DDR 全帧导出/上传，必须另行设计独立的调试或离线导出协议，包括长帧流式读 DDR、分块传输、上位机分块接收、MD5/CRC 和 Frame 边界校验；不能悄悄复用现有 DSP NREAD 上传接口。

## 9. 给 Linux 同事的明确结论

请按以下口径实现，不要再把 PL 完整 Frame、Frame DDR 调试副本和 DSP NREAD 返回结果当成同一种数据：

```text
1. PL 波束数据产生后，逻辑上同时进入两条路径：
   a) Frame DDR：完整 Frame 调试留存；
   b) SRIO/SWRITE：完整 Frame 发送 DSP。
2. Frame DDR 不是正式 Linux 上传源；正式工程不上传 Frame DDR 中的 600 m 完整 Frame。
3. Linux 正式上传源只有 NREAD DDR 中 DSP 返回的数据。
4. frame_bytes/frame_ddr_bytes 与 nread_bytes/upload_bytes 必须分开维护。
5. DSP 返回最大按 4 MiB 约束，实际上传以 NREAD_LAST_BYTES 为准。
6. 正式上传采用分块读取，禁止把长 Frame 放入固定 30 MB 整帧缓存。
7. Frame DDR 只由调试工具按需读取，且不能修改原始数据或干扰业务所有权。
8. 新 24B 格式按 BUILD_ID 分流；正式上传保留原始 NREAD 数据。
9. IRQ 必须读取 EVENT_COUNT 并完成 IRQ_STATUS W1C，再重新使能 UIO。
10. ROLL_INTERVAL 和动态 Roll source_index 按 PL 定义实现。
11. frequency_code 必须根据 fc_kHz/10 正确下发。
```

在以上边界确认前，不建议把当前 `src/app` 作为正式 0x124 Linux 交付版本固化到板卡。

## 10. 一句话判定标准

```text
PL 的 Frame DDR 写入 = 调试留存；
PL 的 SWRITE = DSP 输入；
DSP 的 NREAD DDR 写入 = Linux 正式上传输入；
Linux 不把 Frame DDR 的完整 600 m 数据当成正式上位机上传数据。
```

**ChatGPT 结论：**“边发 DSP 边写 DDR”不等于“Linux 要从 DDR 上传整帧”。当前正式工程只上传 DSP NREAD 返回结果，Frame DDR 只用于调试阶段查看和核验。
