# 协作记录与需求通知机制

## 1. 解决什么问题

PS Codex 和 PL Codex 不是常驻进程，不能像即时通讯软件一样主动弹消息唤醒对方。因此双方使用固定链路：

~~~text
工程师提出需求
    ↓
GitHub Issue 提醒另一位工程师
    ↓
docs/协作记录/请求/ 保存正式请求
    ↓
目标工程师启动自己的 Codex 并要求拉取、读取请求
    ↓
Codex 分析、回复或实现
    ↓
提交并推送 main
    ↓
另一位工程师收到 GitHub 通知，再启动自己的 Codex
~~~

工程师负责提出需求、裁定关键接口和启动本机 Codex；Codex 负责读取请求、修改自己负责的目录、提交结果和留下记录。

## 2. 四种信息分别放在哪里

### GitHub Issue：提醒人和跟踪任务

用于让另一位工程师知道有新需求，适合写标题、背景、负责人和进度。Issue 不用于合并代码，也不替代正式接口文档。项目不使用 Pull Request。

建议标题：

~~~text
[PL-PS-001] 新增 RESULT_LENGTH 寄存器
[PS-PL-002] 需要 PL 提供 DSP 结果帧定义
~~~

在 Issue 中使用 GitHub 的 @用户名提及工程师；仓库网页中把 Watch 设置为 All activity，才能及时收到仓库活动通知。

### docs/协作记录/请求/：让 Codex 能读取的正式请求

每个跨 PS/PL 的新需求或问题建立一个独立文件：

~~~text
docs/协作记录/请求/
├── PL-PS-001-新增结果长度寄存器.md
├── PS-PL-002-DSP结果帧确认.md
└── PL-PS-003-IRQ清除时序.md
~~~

这个文件是 Codex 读取的正式任务入口。Issue 关闭后，请求文件仍保留。

### docs/数据链路/：正式接口结论

寄存器地址、位定义、数据帧、DMA、IRQ、DSP 输入输出、错误和复位行为等内容，确认后必须写入这里。请求文件记录需要定义什么，不能代替正式接口文档。

### Git 提交：代码和配置状态

代码、配置、文档和测试结果都通过提交进入 main。提交号用于让另一边准确找到本次变更。

## 3. 新需求的统一流程

### 第一步：工程师登记需求

提出需求的工程师先建立 GitHub Issue，再在本地仓库创建请求文件。若需求会改变 PS 可见接口，例如新增寄存器、修改位定义、结果长度、IRQ 或 DMA，必须先登记，不得直接让 Codex 修改代码。

### 第二步：发起方启动自己的 Codex

先拉取 main：

~~~powershell
git switch main
git pull --ff-only
~~~

给发起方 Codex 的提示词：

~~~text
请处理 docs/协作记录/请求/PL-PS-001-新增结果长度寄存器.md。
先读取请求、docs/数据链路/ 和对方负责目录，分析影响范围。
当前是接口需求，先不要猜测实现。请把已知信息、缺失信息、需要工程师裁定的内容和建议方案写回请求记录，并说明下一步需要谁完成什么。
~~~

Codex 只提交它负责的目录和请求文档，再推送 main。

### 第三步：目标工程师收到通知

目标工程师通过 Issue、@提及或 Push 通知知道新请求。Codex 不会因 GitHub 有新提交而自动运行，所以目标工程师必须主动打开自己的 Codex。

目标工程师执行：

~~~powershell
git switch main
git pull --ff-only
~~~

给目标 Codex 的提示词：

~~~text
请检查最新的 main，读取 docs/协作记录/请求/PL-PS-001-新增结果长度寄存器.md。
这是 PL 与 PS 的接口协作请求。请只修改 pl/ 和规定的 docs/ 目录，不要修改 ps/。
请核对当前 PL 配置、寄存器导出和 PS 侧读取方式，给出明确结论。
没有工程师裁定的信息先列为待裁定，不要自行猜测。
~~~

### 第四步：工程师裁定

以下内容必须由 PS/PL 工程师裁定：真实 IQ 格式、DSP 输入输出、最终寄存器地址、DMA 缓冲区和 Cache、IRQ 时序、复位、超时、溢出、丢帧、错误恢复、性能指标和硬件验收。

工程师把裁定结果写入请求文件，并同步到 docs/数据链路/。状态变成双方确认后，才允许 Codex 进入接口实现。

### 第五步：执行和交接

接口确认后：

- PL Codex 修改 pl/，更新寄存器和 PL 接口文档；
- PS Codex 拉取 PL 提交，修改 UIO、设备树、寄存器结构、DMA、中断、数据解析和显控上传。

实现方必须在请求文件中填写：

~~~text
实现提交：
修改文件：
PL build ID：
协议版本：
验证方法：
需要对方检查的内容：
~~~

然后提交并推送 main。另一方工程师收到通知后，启动自己的 Codex 拉取和检查。

### 第六步：关闭请求

双方完成检查和硬件验证后，在请求文件中填写最终提交号和验证结果，把状态改为已实现或已验证，在 GitHub Issue 中写入提交号并关闭 Issue。关闭 Issue 不删除请求文件和接口文档。

## 5. PL 新增寄存器的实际例子

假设 PL 需要新增 RESULT_LENGTH 寄存器：

1. PL 工程师建立 Issue：[PL-PS-001] 新增 RESULT_LENGTH 寄存器；
2. 建立对应请求文件；
3. 写清楚地址、位宽、单位、复位值、读取时机和新增原因；
4. 让 PL Codex 先分析，不直接修改 PS；
5. PS/PL 工程师确认地址、含义、数据长度和兼容方式；
6. 把结论写入 docs/数据链路/寄存器协议.md；
7. 把请求状态改为双方确认；
8. 让 PL Codex 实现 PL，填写 PL commit 和 build ID；
9. PS 工程师让 PS Codex 拉取 main，完成 UIO 和寄存器读取；
10. 双方硬件验证后关闭 Issue。

PL Codex 不能只提交新增寄存器四个字。PS Codex 至少要知道地址、偏移、位宽、单位、有效时机、复位值、错误值、build ID 和协议版本。

## 6. Codex 什么时候知道有新任务

Codex 只有在被启动并收到提示词后，才会读取新任务。双方必须遵守：

- GitHub Issue 通知工程师；
- 工程师启动本机 Codex；
- Codex 执行 git pull；
- Codex 读取 docs/协作记录/请求/；
- Codex 分析或实现；
- Codex 提交并推送；
- 另一位工程师重复这个流程。

不要期待 PL Codex 自动弹消息给 PS Codex，也不要把关键需求只写在聊天窗口里。

## 7. 日常最短启动指令

工程师看到新请求后，可以把下面内容发给自己的 Codex：

~~~text
请先拉取 origin/main，检查 docs/协作记录/请求/ 下新增或状态变化的请求。
本次处理请求编号：PL-PS-001。
读取请求及相关数据链路文档后，先给出影响分析。
如果涉及未裁定的寄存器、数据格式、DMA、IRQ、DSP、错误或性能问题，暂停实现并列出待工程师裁定项。
接口确认后，只修改你负责的目录，完成检查、提交和推送，并在请求文件中填写提交号和验证结果。
~~~

## 8. 不使用的方式

- 不把关键需求只发在聊天、微信或口头沟通中；
- 不让 Codex 根据一句模糊话直接修改跨边界接口；
- 不通过修改对方代码目录来通知对方；
- 不使用强制推送覆盖对方提交；
- 不把 GitHub Issue 当作正式寄存器协议；
- 不要求没有运行的 Codex 自动响应。
